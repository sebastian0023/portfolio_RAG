# ADR-049: HTTP wire format and status semantics for the chat stream

Status: Accepted (Phase 3, plan decision 2026-10-04). Extends ADR-048. Updated in Phase 4 (ADR-051, ADR-052): guests only, a guest pass, and the `POST /api/guest-pass` route.

## Context

ADR-048 defines the events but not how they travel. Phase 3 puts the API behind CloudFront with OAC (ADR-004, ADR-013). The OAC spike showed that CloudFront signs the request body, so the browser must send the body hash, and that `Authorization` never reaches the function. The browser needs one parser for success and for refusals, and the API must stay cheap to refuse.

## Decision

**Request.** `POST /api/chat` with `Content-Type: application/json`, `x-amz-content-sha256` set to the lowercase hex SHA-256 of the exact body bytes, and the guest pass in `X-Auth-Token` (ADR-052). The body is at most 8,192 bytes (`MAX_REQUEST_BYTES`, also `limits.requestMaxBytes`).

**Response framing.** Data-only Server-Sent Events: each event is `data: <single-line JSON>\n\n`. No `event:`, `id:`, or `retry:` fields. Comment lines may appear and are ignored. The browser uses `fetch` with a streaming reader, not `EventSource` (which cannot POST), and never reconnects. Headers: `content-type: text/event-stream; charset=utf-8`, `cache-control: no-store`, `x-content-type-options: nosniff`. No CORS headers are ever sent: the SPA and the API share one origin.

**Success.** HTTP 200 carrying `accepted`, optional `sources`, any number of `delta`, then `done` or `error`. Any failure after `accepted` is an `error` event with code `interrupted`.

**Refusals before the answer begins.** A non-2xx status with exactly one `error` event:

| Situation                                                                    | Status              | Error code           |
| ---------------------------------------------------------------------------- | ------------------- | -------------------- |
| Content type is not `application/json`                                       | 415                 | `unavailable`        |
| Body over the byte cap                                                       | 413                 | `too_long`           |
| Body is not valid JSON, or fails the schema                                  | 400                 | `unavailable`        |
| Question longer than the limit                                               | 400                 | `too_long`           |
| Chat off, config missing or invalid, no provider, no trusted IP, store error | 503                 | `unavailable`        |
| Per-minute rate limit                                                        | 429 + `Retry-After` | `rate_limited`       |
| Missing, forged, expired, or other-network guest pass                        | 403                 | `guest_check_failed` |
| Visitor's own daily quota used up                                            | 429                 | `quota_exhausted`    |
| Site-wide daily quota used up                                                | 429                 | `site_limit`         |
| Method other than POST, including `OPTIONS`                                  | 405 + `Allow: POST` | `unavailable`        |
| Unknown `/api/*` path                                                        | 404                 | `unavailable`        |

**Meaning of two fields.** `accepted.quota` carries the visitor's own count for the day: `left` is the per-IP daily limit minus what this visitor has used, and `limit` is that limit (10). The site-wide daily limit (50) is refused as `site_limit` (ADR-051). `done` is `{coverage: "none", cited: []}` because the answer is ungrounded until retrieval exists (Phase 5).

**The guest pass route.** `POST /api/guest-pass` takes `{"token": "<Turnstile token>"}` (at most 2,048 characters) with the same body-hash header, and answers JSON that is never cached: `200 {"pass": "...", "expiresAt": <epoch seconds>}` or a refusal `{"error": "<code>", "retryAfterSeconds"?: n}` with status 400 (bad body), 403 (`guest_check_failed`), 413, 415, 429 (`rate_limited`), or 503 (`unavailable`). Other methods get 405 with no CORS headers.

**Client rules.**

- Validate every event with `chatStreamEventSchema` (ADR-048).
- `fetch` rejecting with a `TypeError` is a `NetworkError` (ADR-048 item 4).
- A non-SSE 429 (the Lambda reserved-concurrency throttle) maps to `rate_limited` with a 10 second retry.
- Any other response that is not an SSE stream (CloudFront 403, 502, or 504, a Lambda init failure) is a `NetworkError`.
- A stream that ends without `done` or `error` is treated as interrupted.

## Consequences

- One parser serves success and refusal. The status code lets the edge, logs, and tests tell refusals apart without reading the body.
- The browser must hash the exact bytes it sends, so request fitting (dropping old history) happens before hashing.
- A 4xx or 5xx from the API with an SSE body is a refusal; a 4xx or 5xx without one comes from the edge or the platform.
- Changing a status or the framing is a contract change: update `packages/shared/src/sse.ts`, the API tests, the web transport, and this ADR together.
