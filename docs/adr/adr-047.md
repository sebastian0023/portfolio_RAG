# ADR-047: Share the owner's existing AWS account with enforced isolation

Status: Accepted (Phase 1, owner decision 2026-10-04). Supersedes the dedicated-account clause of ADR-032 and resolves O-05 as "existing shared account".

## Context

ADR-032 assumed a dedicated AWS account so that quota, budget, and blast radius belonged to this project alone. A read-only audit on 2026-10-04 found that the owner's existing account is not empty:

- It hosts several unrelated projects (serverless apps, Terraform state buckets and lock tables), and an earlier live portfolio under the `dsmm-portfolio-*`, `portfolio-gha-tf-*`, and `portfolio-mp3-*` names.
- One GitHub OIDC provider already exists and is trusted by ten roles belonging to other projects. An account can hold only one provider per URL.
- An unrelated monthly budget exists. Cost-allocation tags `Application`, `Environment`, and `CostScope` are already active.
- Root MFA is enabled and there are no root access keys. The IAM user behind the CLI profile has no MFA device. AWS Organizations and IAM Identity Center are not enabled.

The owner chose to deploy portfolio v2 in this account rather than create a dedicated one.

## Decision

Use the existing account, with isolation enforced by convention, IAM scope, and tests instead of by an account boundary:

1. **Naming.** Every resource is named `portfolio-v2-<env>-<concern>` with `env` defaulting to `prod`. S3 bucket names add a random suffix. The prefix `portfolio-v2-` is distinct from every existing `portfolio-*` name.
2. **Tags.** The Terraform provider applies default tags `Application=portfolio-v2`, `Environment=prod`, `CostScope=portfolio-v2-prod`, and `ManagedBy=terraform`. The first three reuse keys that are already active for cost allocation.
3. **Shared OIDC provider.** Terraform reads the existing GitHub OIDC provider through a data source and never creates, modifies, or destroys it. Plan and apply roles are new, named with the prefix, and trust only this repository, using the `repository_owner_id` and `repository_id` claims in addition to `sub`, as the existing roles do.
4. **Scoped permissions.** Roles created for this project can act only on `portfolio-v2-*` resources wherever the service supports resource-level scoping. Actions that require `*` are listed explicitly in review. Nothing in this repository reads, modifies, or deletes resources outside the prefix, including other projects' state buckets and lock tables.
5. **State.** A dedicated bucket `portfolio-v2-prod-tfstate-<suffix>` with a native lockfile. No existing state bucket or lock table is reused.
6. **Budget and kill switch.** An account-wide budget is not used, because other projects' spend would trip it. Instead (a) a monthly budget filtered on `CostScope=portfolio-v2-prod` covers tagged resources, and (b) a monthly budget filtered on the Bedrock service deliberately over-approximates model spend, since on-demand inference cannot be tagged. Other projects' Bedrock usage can therefore trigger the kill early; that fails safe because the deny policy attaches only to `portfolio-v2-*` roles. P1-01 and P3 evaluate taggable application inference profiles for exact Haiku attribution. Mantle (Gemma) attribution is unverified.
7. **Human access.** A role named `portfolio-v2-prod-operator` is created once by hand, because it must exist before Terraform can run. Only the owner's IAM user can assume it, only with MFA authenticated in the last hour, and sessions last one hour. AWS Organizations and IAM Identity Center are not enabled: they would change the whole account, and SSO to an account needs an organization instance. The IAM user's long-lived key is used only to assume this role; Terraform, scripts, and CI never use it directly. Existing IAM users, roles, and keys are not changed.

## Consequences

- R-10 (blast radius) widens: another project's mistake, quota use, or spend can affect v2, and a v2 mistake can affect them. The owner accepts this. P1-11 adds a plan check that fails when a planned change touches a resource outside the prefix or a protected shared resource.
- Lambda account concurrency (default shared across the account) and Bedrock quotas are shared; reserved concurrency for v2 reduces what other projects can use. Record actual quotas in P1-01.
- Billing attribution is imperfect and lags, so quotas (real-time admission control) remain the primary cost defense and the budgets remain a backstop.
- Revisit in Phase 7: moving to a dedicated account is a reviewed migration under ADR-033, not an in-place change.
- P1-02, P1-05, P1-08, and P1-11 acceptance criteria are interpreted with this ADR.
